# SailDoom: SQLDoom on Sail, the full report

SQLDoom ([cedardb/sqldoom](https://github.com/cedardb/sqldoom)) is CedarDB's
port of Doom to SQL: the renderer is one query, the game logic is about 5,900
lines of CedarScript over some 40 tables, and a small Python client only reads
the keyboard, drives the tics and shows the bitmap. All the credit for Doom in
SQL belongs to SQLDoom. SailDoom runs that work on
[Sail](https://github.com/lakehq/sail), a Spark-compatible engine on Apache
DataFusion, as Spark SQL over Spark Connect, and checks every step against
SQLDoom on CedarDB, which serves as the exact oracle: every pixel and every row
of every tic either matches or it does not.

This report covers the whole effort: the renderer, the game as one recursive
query, SQLDoom's database API on Sail, SQLDoom's own client playing on Sail,
the performance work that took a tic from 7 s to about 31 ms, the changes in
the Sail fork, and what was filed upstream. Measurements come from
[NOTES.md](../../NOTES.md); findings about Sail, DataFusion and Arrow are
collected in [DDD.md](../../DDD.md).

## 2. The renderer

SQLDoom renders a frame as one query: BSP traversal, wall, floor, ceiling,
sky and sprite spans, texture lookups, lighting, the weapon and the status
bar. The port is Spark SQL over the WAD's tables in Parquet.

### Port

- `sql/renderer_v1.sql` is the stage-by-stage port: pixel-exact, 9.8 s a
  frame. The dialect differences are explicit: Postgres divides integers as
  integers and rounds half to even when it casts a float to an integer, Spark
  does neither (`DIV`, `bround`); `generate_series` becomes a guarded
  `explode(sequence(...))` (the `GS` macro); `GET_BYTE` on texture blobs
  becomes a join on a texel table; `LATERAL ... LIMIT 1` becomes a window and
  a join.
- `sql/renderer.sql` computes the same pixels as one stream, every heavy stage
  read once: Sail inlines a CTE at every reference, and SQLDoom's renderer
  reads its heavy stages many times (inlined, the EXPLAIN text was 8.4 MB).
  Seed rows instead of joins back, `explode(array(...))` instead of
  `UNION ALL` of filters, windows instead of self-joins, one texel table.
- `sql/renderer_batch.sql` (generated by `scripts/make_batch_renderer.py`)
  draws many frames per query from a `frames` relation of poses.

| Version | One frame | Notes |
|---|---|---|
| CedarDB, SQLDoom's own query | 32 ms | in Docker's Linux VM |
| `renderer_v1.sql`, stage-by-stage port | 9,800 ms | pixel-exact |
| `renderer.sql`, one stream | 1,570 ms | pixel-exact |
| the same, one-row side first in cross joins | 708 ms | pixel-exact |
| `renderer_batch.sql`, 35 frames a query | 58 ms a frame | 10 cores |
| `renderer_batch.sql`, 105 frames a query | 41 ms a frame | one client: 24.3 frames/s |
| the same, 2 clients concurrently | 29.5 ms a frame | 33.9 frames/s |
| the same, 4 clients concurrently | 25.8 ms a frame | 38.8 frames/s |

What cost time on Sail main, found by profiling a symbolized build: CTE
inlining; a cross join emitting one batch per row of its left input (putting
the one-row side first took a frame from 1.6 s to 0.7 s); and planning rather
than execution (parsing about a third of a frame's request, physical planning
another third). Batching answers planning for throughput, since the plan is
the same size for 1 or 105 frames.

### Exactness

- Pose literals: SQLDoom's client sends the camera pose as decimal text, and
  CedarDB converts `215.18106079101562` to `0x406ae5cb3fffffff`, one ulp below
  the correctly rounded double. Sail's `CAST(215.18106079101562 AS DOUBLE)`
  gives the same bits, so the batch renderer takes its poses through the same
  literal cast.
- The 5 differing frames of 526: at tic 42 `cos(-radians(336.0))` is `...7f95`
  with Apple's libm and `...7f96` in CedarDB (glibc); at tic 53 `tan` differs
  in its last bit. A flipped last bit moves a `FLOOR` across an integer. Running
  Sail on Linux should close these; not checked yet.
- Release `v0.1-renderer` has the renderer videos (`saildoom-e1m1.mp4`, and
  `saildoom-vs-cedardb-e1m1.mp4` with the difference in red).

Commits: `d36d7d8` (renderer, pixel-exact), `fe29708` (one stream),
`357612e` (batch renderer), `1e2b000` (concurrent clients).

## 3. The game as one recursive query

### The world as one relation

The tic runs over a world held as one relation (`saildoom/world.py`): one row
per thing of state, one struct column per kind of state. Twenty kinds are the
world proper (player, sectors, movers, line events and activations, switches,
sidedefs, render segs, Things, their health, monster AI, render Things,
effects, weapons, owned weapons, picked-up items, secrets, automap lines,
projectiles, monster deaths); the API backend adds the per-tic staging tables
SQLDoom keeps, 35 kinds in all. Each row fills only its own kind's column.

SQLDoom's stages become CTE chains over that relation, in tic order:
`sql/tic_doors.sql`, `tic_step.sql`, `tic_combat.sql`, `tic_projectiles.sql`,
`tic_sound.sql`, `tic_monsters.sql`, `tic_out.sql` (and `tic_staging.sql` for
the backend). CedarScript `if`s and plan bits become per-tic gates (a CTE of
the tics on which a stage runs); `INSERT ... ON CONFLICT` and `UPDATE` become
joins that produce the next version of a kind. A whole run is one
`WITH RECURSIVE` query: tic 0 and the player's commands go in, every later tic
is computed by Sail. `sql/level_start.sql` computes tic 0 from the map's
tables on Sail as well.

### The Sail fork

Sail main has no `WITH RECURSIVE`. The fork
([querygraph/sail `work/recursive-cte`](https://github.com/querygraph/sail/tree/work/recursive-cte))
adds it, then fixes what the game found:

| Commit | Change |
|---|---|
| `150345a83` | recursive CTEs (`WITH RECURSIVE`) |
| `e0c9e9fd7` | a recursive term may refer to its CTE more than once (a shared work table) |
| `d7d7e7cf8` | a CTE referenced more than once is computed once (it was inlined at every reference) |
| `10fe27c9d` | CTEs that read the work table were treated as self-references and inlined, which grew the tic's plan exponentially |
| `f0c5e7567` | a shared CTE defined outside an inner recursive query was reset from inside it and its consumed plan run again (a `RepartitionExec` panic); the owner resets it |
| `2285f2330` | DataFusion's `AggregateExec` keeps its MIN/MAX dynamic filter through `reset_state`, so a recursive term's later iterations scanned with the first one's bound (a barrel's blast found no blast radius); the fork turns that pushdown off in plans with a recursive query ([apache/datafusion#26054](https://github.com/apache/datafusion/issues/26054)) |

Measured against Sail main, both release builds (fat LTO), same machine:

| Workload | Sail main | Fork |
|---|---|---|
| Renderer, stage by stage (`renderer_v1.sql`) | 10,183 ms | 4,118 ms, same pixels |
| Hand-restructured renderer (`renderer.sql`) | 698 ms | 733 ms |
| Batch renderer, 105 frames a query | 45.4 ms/frame | 39.3 ms/frame |
| Game tic, 525 tics as one recursive query (player only) | not supported | 33.0 s (63 ms/tic) |
| The whole game, 1,200 tics as one recursive query | not supported | 202 s (168 ms/tic) |
| TPC-DS SF1, the 22 queries that reuse a CTE | 2,794 ms | 2,870 ms (noise) |
| TPC-DS SF1, 4 control queries | 118 ms | 123 ms |

TPC-DS results are identical on both for all 26 queries.

### Exactness

Three checks (`reference/check_tic.py`):

- `--mode step`: every tic computed from CedarDB's recorded state at the tic
  before, all in one query (1,200 tics in 18 s);
- `--mode recursive`: the whole run as one recursive query from tic 0;
- `--mode played`: only the recorded commands go in, the level start too is
  computed on Sail.

On a 1,200-tic E1M1 run (45 shots with chaingun, shotgun and rockets, 14
kills, imps throwing fireballs, barrels chaining, doors, a lift, pickups, a
secret) every row of all world tables matches CedarDB at every tic. Tours
recorded with a bot (`reference/bot.py`, `reference/record_run.py --tour`)
check the specials E1M1 never triggers: E2M3 (crushers, lights, teleports),
E2M4 (stairs, raises), E2M7 (ceilings), and a mortal Nightmare E1M1 run
(death, Nightmare respawns). Donut and stop specials appear on no Freedoom map.
The Sail-played run renders to the same frames, byte for byte, as Sail
rendering CedarDB's recorded state; release `v0.2-game` has the video of the
1,200-tic run, every tic computed and every frame drawn by Sail.

The port had to reproduce CedarDB's arithmetic, found by probing it:

- `real` combined with an integer or a decimal literal stays `real`, and
  `POWER` and `SQRT` of a `real` are `real` (Postgres widens to double):
  single precision throughout, `FHYPOT` in `saildoom/sqlmacro.py`;
- casts to an integer truncate; `ROUND` of a double rounds half away from
  zero;
- the bot's float commands reach CedarDB as decimal text, which rounds to
  `real` directly; the port reads commands back from `game_tic_commands`;
- the camera interpolates `real - real` in single precision.

A DataFusion bug surfaced here too: an inner join whose `ON` pairs an
equi-key with an equality spanning two cross-joined relations loses the second
equality, returning wrong rows
([apache/datafusion#26058](https://github.com/apache/datafusion/issues/26058));
the respawn fog is written as one branch per fog instead.

Commits: `4cb4e5e` (first tic), `89a01b5`, `8863089`, `6e96e0c` (the whole
game), `686f0d2` (every line special, crushing, death, Nightmare respawns,
E1M8's boss floor), `7eff091` (level start on Sail), `802e6bc`.

## 4. SQLDoom's database API on Sail

The game as one query covers the tic. SQLDoom's client also uses menus, level
flow, intermission, finale, save and load, demos, cheats, sound queries and
the automap: about everything in `doom_sql.py`. `saildoom/backend.py` answers
each statement the client prepares, and the raw SQL it sends, from Parquet
tables on Sail; `install(doom_sql, backend)` swaps the backend in.

- Tables are versioned Parquet files in a store; a statement's writes produce
  the tables' next versions.
- A game tic runs the same tic SQL as the recursive query, for one tic, plus
  `tic_staging.sql` for the staging tables SQLDoom keeps.
- `saildoom/api/` holds the rest: menus, level flow, screens (intermission,
  finale, weapon slots, demos, cheats), saves (with the render caches rebuilt
  on load), the automap and its renderer (`client/render_automap.sql`), and
  the screen renderer (`client/render_screen.sql`: title, menus, load/save,
  help, intermission, every finale stage).

### Exactness method

`reference/trace_api.py` records a scenario on CedarDB: every call, the rows
it returned, and every table it changed (snapshots sorted, filtered to the
scenario's maps). Rendered frames are recorded by their SHA-256 digest with
the bytes kept beside the trace. `reference/check_api.py` replays the trace on
Sail and compares call by call: returned rows and every changed table.

| Trace | Calls | Result |
|---|---|---|
| `menus` | 509 | all match |
| `campaign` | 4,314 | all match; E1M1 with cheats, weapon slots and the automap, exit and intermission, E1M2 carried over, saved and loaded, the secret exit, E1M8 and the finale, a demo recorded and played back by the attract loop; one call returns doubles a few ulps apart (libm) |
| `automap` | 526 | all match; ten frames (grid, pan, zoom, fit, both IDDT levels) byte-identical |

`reference/check_screens.py` renders 68 title, menu, load/save, help,
intermission and finale pages on both engines from the same `screen_state`:
all byte-identical.

More CedarDB behaviour the backend reproduces:

- a decimal literal sent as a parameter becomes a `real` as f32(mantissa) /
  f32(10^k) when written plainly, nearest when written with an exponent (a
  different float a third of the time; `cedar_real`, probed against 2,000
  values);
- numeric division truncates to an operand-dependent scale (`200.0/2048.0` is
  `0.0976562`; the automap arrow's `8.0*16.0/7.0` is `18.285714`);
- void functions return `''`; `real` is returned as its shortest text;
- `sound_events`' `BIGSERIAL` consumes a value for every attempted insert,
  including rows `ON CONFLICT DO NOTHING` drops; CedarDB's order among one
  tic's inserts follows its plan, so event ids are compared as a set per tic;
- `ARG_MAX` ties are broken arbitrarily in CedarDB; the automap's are made
  deterministic with a secondary key.

Commits: `820c4c4` (backend, recorder, replay checker), `0d26cf2`, `b68cead`,
`8ad1470`.

## 5. Playing SQLDoom's own client

`saildoom/pgshim.py` stands in for psycopg2: prepared statements go to the
backend, registered raw SQL to its handlers, other `SELECT`s run on Sail with
their parameters bound. `scripts/play.py` runs SQLDoom's client unchanged on
it (`--headless --scripted` drives it through the menus into E1M1 and plays,
for tests), and `scripts/play-sail.sh` starts the fork's server unless one is
listening, opens the game window, and stops the server it started on exit.

The first headless run played from the title screen into E1M1 at about 7 s a
tic and 0.9 s a frame (`86d07b1`).

## 6. The performance journey

### Where the time was

Nearly all of a tic was Sail planning the tic query: 710 KB of SQL, 312 CTEs,
6.5 s; running it is cheap (the same SQL steps 1,200 tics in 18 s when planned
once). A profile on a symbolized fork build: logical optimizer 46%, physical
planning 36%, Sail's resolver 18%; a quarter of all samples compared struct
literals. Every `UNION ALL` branch of the world's packing carries a
`CAST(NULL AS STRUCT<...>)` for each other kind, and
`EquivalenceProperties::project` registers each as a constant and compares it
with every other through `StructArray::eq`, which converts both arrays to
`ArrayData` before comparing anything. Rewriting the SQL did not help (each
kind from its own table planned in 15 s; non-literal placeholders in 11.7 s).
The fix belongs in DataFusion: compare types first
([apache/datafusion#26065](https://github.com/apache/datafusion/issues/26065),
PR [#26066](https://github.com/apache/datafusion/pull/26066), vendored in the
fork): planning went from 6.5 s to 4.7 s. Planning every tic could go no
further, so the tic is planned once and run every tic.

### Planned once, run every tic

The fork's plan reuse (`sail_common_datafusion::plan_reuse`): slot views hold
a view's rows in memory on the server and are read when a plan runs; the plan
cache keeps a query's physical plan and runs it again with its operators'
state reset. The tic runs in a Spark session of its own
(`saildoom/api/tic_engine.py`) whose inputs are all slots, with one DataFrame
per level run every tic; the renderer does the same with
`sql/renderer_batch.sql` and a one-row pose slot (`saildoom/api/render.py`).

Step by step, a cached tic run alone, and the client's steady-play rate where
it was measured:

| Step | Tic (alone) | What it removed | Client |
|---|---|---|---|
| Start | 7 s | | |
| Plan reuse | 1.1 s | analysis, optimization, physical planning | |
| Cache looked up before parsing | 0.55 s (est.) | parsing 710 KB of SQL on every run | |
| One partition, no tracing, reset keeps properties | 0.10 s | repartitioning, per-operator tracing, recomputing every node's properties | |
| Frames on a kept plan (0.83 s to 0.09 s a frame) | | | ~5 tics/s |
| Client queries from Arrow, unchanged tables left alone | 0.10 s | four small queries a tic planned on Sail (67 ms in the client) | ~8 tics/s |
| Only changed kinds returned, cache key hashed | 0.09 s | 6.8 MB of null struct columns a tic (now 0.5 MB) | |
| Cheap output-bytes metric (vendored DataFusion) | 0.061 s | converting every struct column to `ArrayData` in every operator, every batch | |
| Slots uploaded from Arrow; writes split by map, in the background | 0.058 s | the server reading back files just written; rewriting 141,000 `render_segs` rows of other maps | |
| Definition tables as slots | 0.055 s | reading 25 definition tables' files on every run | 17.1 tics/s |

Frames went from 0.83 s (planned every time) to 0.17 s on a kept plan and
0.09 s with four partitions; in steady play the client shows about 9.7 frames
a second (it draws once per pass of its loop and runs up to four tics a pass).

### What did not help

- Rewriting the world's SQL to avoid the struct literals (slower plans, above).
- Moving the renderer into a process of its own (`RenderProcess`): a tic runs
  in 55 ms alone and about 60 ms while another session renders, whichever
  process the renderer's client is in, so the contention is on the server.
- A shorter GIL switch interval in the client.
- Merging projection pairs: of 147 projection-over-projection pairs, 7 could
  be merged for free; in the others both sides compute.
- The game loop as one never-ending recursive query (considered, dropped): a
  recursive iteration costs about what a cached tic now does.

### Where the time is now

A tic run alone: about 22.6 ms running the plan and receiving its result
(3,544 operators; a request alone costs about 4.4 ms), the rest Python. A
level's first tic plans the tic query, about 5 s, once a level.

## 7. The fork's conventions

Opt-in only; no standard Spark behaviour changes otherwise. All experimental.

| Convention | Where | What it does |
|---|---|---|
| `spark.sail.slotViews` | session setting | named temporary views keep their rows in memory on the server (slots), read when a plan runs |
| `spark.sail.planCache` | session setting | keeps each query's physical plan, keyed by a hash of the relation (without the client's plan id); a repeat is not parsed or planned; inputs that are not slots must not change while on |
| `spark.sail.targetPartitions` | session setting | partitions cached plans are planned for |
| `/* sail.result_slot=NAME */`, `/* sail.result_slot=NAME:CTE */` | leading SQL comment | the result, or the rows computed for shared CTE `CTE`, go to slot NAME |
| `SAIL_EXECUTION_METRICS=off` | server environment | operators register no execution metrics and do not time polls |
| `__slot_NAME` named arguments (Arrow IPC, binary) | query arguments | fill slot NAME before a cached plan runs; left out of the cache key |

Changes needing no convention, applying to every query: recursive CTEs and
CTEs computed once; column-only projections folded into CTE references and
slot scans, cooperative in-memory leaves, merged projection pairs; slot row
counts for the join planner; and vendored DataFusion 55.1.0 crates
(datafusion-common: nested scalar equality and buffer-based memory counting;
datafusion-physical-expr-common: a cheap output-bytes metric and the metrics
switch). The fork's function feature tests pass (5,375 with metrics off, where
three `EXPLAIN` tests that expect metrics fail; they pass with metrics on).

## 9. Not done

- **Deathmatch and the multiplayer API** (`39_mp.sql`, `42_api.sql`), item
  respawn, and a trace for them; level stats are not covered by a trace.
- **Loading a WAD without CedarDB**: the map and game tables come from
  CedarDB's export today.
- **35 tics a second**: a tic is 27 ms run alone, about 31 ms in the client.
  The next step written down is a narrow world (a relation per kind instead of
  one with 34 NULL struct columns a row), estimated at 5 to 8 ms a tic; its
  plan, and the measurement to do first, are in [DDD.md](../../DDD.md).
- **One renderer frame** of the 1,200-tic run (tic 730) draws the floor under
  the player with the wrong flat (17,443 pixels); it does so from CedarDB's
  own recorded state too, so it is the renderer, not the game.
- **libm last bits**: running Sail on Linux (glibc) should close the
  remaining renderer differences; not checked.
